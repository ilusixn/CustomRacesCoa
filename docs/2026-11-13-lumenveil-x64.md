# Lumenveil on x64 (2026-11-13)

Lumenveil (fog, sun/moon shafts, lamp light, water) is GPLv2 and Win32 upstream. It now runs with CoA64 as a separate
**x64 DLL**, `Lumenveil64.dll` beside the exe; the client only loads it and feeds it (`CoA/Source/Runtime/Lumenveil.cpp`,
`Engine/Source/Gx/Lumenveil.h`). Nothing of it is compiled into AFK64.exe.

## Engine side (lumenveil/Lumenveil, branch `port/x64`)

- The 32-bit gate in the CMake configure is gone; a 64-bit build drops `hooks.cpp`'s naked thunks and
  `client_world.cpp` (client-memory readers) and keeps the renderer, shaders, settings and data readers.
- `host_x64.cpp` / `engine_host_x64.cpp` answer the client-memory API from the host table `VfHostX64`.
- The frame events are exported: `vf_on_frame_begin/end`, `vf_on_opaque_begin/done`, `vf_on_liquid_begin/end`,
  `vf_on_liquid_instances_done`, `vf_on_liquid_material`, `vf_on_world_done`, `vf_far_clip_clamp`, `vf_x64_host`.

## Client side (this repo)

`CoA::Visuals::Start()` loads it for `visuals 1` and skips LuxVelum, so the two mods never hook the same frame:

| Input | Source |
| --- | --- |
| device, viewport | `g_theGxDevicePtr` / the D3D9 device |
| view, projection, camera, far clip, map | Gx xforms, `CWorldScene`, `World::s_farClip`, `LoadingScreenMapId` |
| day/night, fog colours, sky, glow, light slot | `DayNight::g_dnInfo` |
| stock fog writes | `DayNight::g_dnInfo` fog groups |
| clock, weather, area, far-clip refresh | inert answers for now (the engine uses the frame inputs) |

Events are called at the same places LuxVelum's callbacks sit in `CGWorldFrame::RenderWorld`
(`frameBegin/End`, `opaqueDone`, `liquidBegin/End`, `worldDone`).

## Testing

`Visuals.txt` beside the exe with `1` (or `-visuals 1`), `Lumenveil64.dll`, `CoAVolFog.ini`, `lampdata.bin` and
`liquiddata.bin` in the game folder. Without the DLL the log says so and nothing changes.
